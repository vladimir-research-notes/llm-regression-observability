Architecture

Data flows one direction: cases plus an adapter produce run records; two runs are compared into comparison records; comparison records render into a report. Every stage writes inspectable JSON/JSONL artifacts so it can be re-run or examined on its own.

status: all three stages are built end to end — schemas (M1), fixtures (M2), adapters (M3), run executor (M4), evaluators (M5), the comparison engine (M6), the report generator (M7) and the observability layer (M8)

Where redaction sits (M9)

traces/redaction.py is one pattern table read by four callers, and it runs in front of every write — never after one.

run.jsonl     mask content, derive redaction_status, refuse if flagged  (executor, before hashing)
spans.jsonl   gate only — every string in a span is a join key          (write_spans)
report.md     mask free text in, gate the rendered document out         (build_report + write_report)
source tree   scan, certain tier only                                   (llmreg scan-secrets)

Why the report reads only the artifacts

The report generator opens comparison.jsonl, summary.json and comparison_meta.json — not the runs, not the fixtures, not the engine. So a report is reproducible from a directory a colleague hands you, and it cannot quietly enrich itself from a source the reader does not have. The cost is visible in the output: the structured-output table shows json_validity_delta = -1 ("was valid, is not") rather than 1.0 → 0.0, because ComparisonRecord records the delta and the flag, not the two absolute values.

Selection — which regressions are "worst", which case represents the tool-call dimension, whether a cost row may be shown at all — happens once, in a shared ReportModel. The Markdown and HTML renderers lay out tables; they do not choose rows. Two formats of one report cannot disagree.

Why the comparison writes three files

summary.json answers what regressed. comparison_meta.json answers what the engine declined to say, and why: which cases went unpaired, which candidates were attributed to infrastructure and had their flags withheld, whether cost was comparable at all (two runs priced under different cost models are not), and which thresholds every rule actually used. Both silences are invisible in the summary's counts, and both are exactly the kind that makes an evaluation harness lie — so they get a file. A comparison with an empty summary and a populated sidecar has found nothing and hidden a lot, and the two together make that impossible to miss.

Why file-based stages

Each stage persists its output before the next begins. That makes the system debuggable (inspect the JSONL), reproducible (re-run any stage on committed artifacts), and portable (a trace imported from another runtime enters at the executor boundary).

Observability spans (Milestone 8)

Spans — request, model call, tool call, retrieval, evaluator — land next to run records so a single case is fully reconstructable. They are a projection of the recorded trace, not a live emission: nothing here instruments a call, because there is no call. build_case_spans() is a pure function of (EvalCase, RunRecord, metrics), and span ids are content-addressed (sha256(run_id | case_id | path)), so two projections of one record are byte-identical.

That purity is why llmreg aggregate, not the executor, writes spans.jsonl: an evaluator span needs a metric, and the executor has never scored anything. Deriving the tree one stage later costs nothing and buys one writer and a complete tree, rather than two writers and two partial ones.

The trace records exactly one duration, latency_ms. So the request span's interval is recorded; its application children get a contiguous partition of that interval in trace order, labeled derived, which asserts ordering and not duration; and evaluator spans are zero-width at the request's end, labeled none, because scoring happens afterwards in the harness. Aggregation then reduces per-case metrics into three separate maps — application scores, harness signals, declared placeholders — which is what makes a degraded harness read as a telemetry problem rather than a false regression.

Adapters (Milestone 3)

An adapter is the only thing standing where a real model would be. It takes an EvalCase and returns a RunRecord, so every stage downstream runs with no model call and no network.

The contract deliberately splits what the model produced from which run this is. AdapterContext holds run identity — app_version, model_id, prompt/tool versions, and the recorded timestamp. AdapterResponse holds behavior — final and parsed output, tool calls, retrieval sources, errors, and token/latency/cost estimates. build_run_record() joins the two. Because the timestamp is an input rather than a call to the clock, determinism is a property of the construction, not a convention someone must remember.

AdapterRole
MockModelAdapterFixed outputs for tests; a deterministic default per case.
RecordedModelAdapterReplays the committed fixture runs verbatim, keyed by (app_version, case_id). Baseline generator.
ScriptedRegressionAdapterInjects one known defect into a clean baseline. Candidate generator, and the ground truth the detector is measured against.
ApiAdapterStubInterface only. Disabled by default; raises either way until Milestone 11.

The scripted adapter is two layers: fifteen small, pure injectors (invalid JSON, dropped/wrong/extra tool, argument drift, order swap, unsupported claim, dropped citation, refusal flip, added latency, added cost, injected error), and an injection plan derived from the Milestone 2 CaseExpectation ground truth. A non-control case receives a representative defect of its annotated category; an infra-attributed case receives an infra-origin error — surfaced, but never a flag (research question 9); a true control receives nothing at all. Each injector moves exactly one dimension, which is what makes "only the annotated field changed" an assertion rather than a hope.

The scripted candidates are not byte-identical to the recorded candidates and do not claim to be. The recorded candidates remain the primary ground truth; the scripted adapter is an independent, mechanical generator of the same defect categories.

Run executor (Milestone 4)

The executor resolves a suite manifest into an ordered EvalSuite, drives one adapter over every case, and writes results/runs/<run_id>/run.jsonl (one RunRecord per case) plus a run_meta.json sidecar carrying identity, totals, the cost model applied, and the SHA-256 of the records. Three questions had to be answered here rather than left to convention.

Who owns run identity? The executor. Adapters emit behavior — the recorded adapter in particular replays fixtures verbatim, including each record's own per-case run_id. The executor re-stamps: every record in a run carries the run's run_id and the configured app_version, so (run_id, case_id) keys the artifact and ComparisonRecord.baseline_run_id denotes exactly one run. model_id, prompt/tool versions and timestamp are provenance, not identity: preserved as the adapter reported them unless overridden, with RunMeta.identity_overrides recording which the caller forced. Absent an explicit --model-id, a synthetic run names the adapter that produced it rather than a model it never called.

Where does latency come from? The recorded input, never the wall clock. Timing the adapter would put an ambient value into a scored field, so artifacts would differ run to run and every latency assertion would become flaky. The executor records latency; it does not measure it. The cost of that choice is written down in Limitations rather than glossed.

When are tokens and cost estimated? Only where the adapter left them at zero — recorded fixture values are inputs, not defaults to overwrite. --recompute-cost forces the cost model over every record, so two runs can be priced under one model regardless of what their adapters claimed. run_meta.json counts how many records took each path, so an artifact never hides which numbers were derived.

Byte-stable persistence lives in exactly one module, traces/storage.py: sorted keys, compact JSONL separators, ensure_ascii=False, explicit UTF-8, and an explicit \n line ending including a trailing one. "Two runs are byte-identical" is therefore a property of one function rather than a convention every caller must remember.

Evaluators (Milestone 5)

Each scorer is a pure function of (EvalCase, RunRecord) — no clock, no RNG, no network, no learned model — emitting MetricResults. evaluate_case() runs all ten modules and returns their results sorted by metric name, so a scored artifact is byte-stable regardless of registration order.

A scorer is silent when the case gives it nothing to score, so the metric set is a property of the case rather than of the registry: a structured case emits three JSON metrics and no evidence metrics. Downstream, an absent metric means not applicable, never zero — the difference between "this candidate has no schema" and "this candidate failed its schema."

Two tables carry the contract forward. METRIC_DIRECTION says which way is worse for each metric, so the comparison engine flags a bad move without hard-coding a sign. NEVER_FLAG_METRICS names what may not raise a regression at all: the two declared placeholders, and the infra counters — harness noise is surfaced, never blamed on the application.

trace_completeness sits slightly apart from the rest: it scores the observation, not the application. Every other metric assumes the trace says what happened; a run whose latency was never recorded scores as the fastest in the suite. A drop there means the harness is broken, which is a different finding than a regression.

Deterministic by construction

No ambient time/random/datetime.now() in scored paths. Timestamps and seeds are inputs recorded in fixtures or run config. Two runs of the same suite on the same fixtures produce byte-identical artifacts except for an explicit run_id — which is what lets "the injected regression was detected" be a stable test rather than a flaky one. The Milestone 3 candidate stream hashes to the same SHA-256 across separate processes, and the Milestone 4 run artifacts are byte-identical across separate processes and output roots.

This is enforced, not merely asserted: a test parses each executor-path and evaluator module's AST and fails if it imports time, datetime, random, secrets, socket, urllib, http, or requests. The executor also re-hashes run.jsonl after writing and raises if the bytes on disk disagree with its in-memory digest, and every metric value is rounded at the boundary so a score cannot differ in the last bit of a float between platforms.

Test / result status

python3 -m pytest -q → 441 passed. The recorded adapter reproduces all 52 committed fixture records exactly; every non-control case receives a real injected defect and every true control receives none. The executor turns the eight-case smoke suite into a baseline and a candidate run whose only differences are the injected defects; the evaluators score each run into results/processed/<run_id>/metrics.jsonl, every injected defect moving exactly the metric it targets; and the comparison engine pairs the two runs into results/comparisons/<id>/, detecting 18 of 18 injected defects across the six fixture suites with 0 false positives on the eight negative controls (see Results).

Open questions / limitations

The scaffold defines the contract; each stage is realized in its milestone. Because the executor re-stamps run identity, a run's run.jsonl is deliberately not byte-identical to the committed data/fixtures/*/baseline.jsonl, whose records carry per-case run_ids — Milestone 3's exact-replay guarantee holds one layer down, at the adapter. The two smoke runs also differ in model_id (recorded-mock-v1 vs scripted-regression-adapter) because provenance is preserved rather than faked. Milestone 6 therefore diffs only comparison.BEHAVIORAL_FIELDS and treats identity and provenance separately: a model or prompt version bump is the thing under test, not evidence of a regression. There is no server or persistence layer beyond local files (an optional SQLite trace index is regenerable). See Limitations.
