Results

status: Milestone 11 complete — 18/18 injected defects detected with their annotated category and severity; 0 false positives on the 8 negative controls; the comparison renders as a deterministic, redaction-gated report; each run projects into a span tree and reduces to suite metrics that keep harness signals separate; a masking redactor runs in front of every write, and 52/52 committed fixture records pass through it unchanged; traces from outside this repository enter through versioned import contracts; and the optional paid-API adapter sits behind seven gates and no network client; 849 tests passing, all offline

Everything below is measured on synthetic fixtures with injected defects. 18/18 recall on a suite built to be detected is evidence that the rules fire as specified and that the negative controls do not — it is not evidence of recall on real regressions in real systems, and no such claim is made. See Limitations.

Detection on ground truth (Milestone 6)

Each fixture suite ships an expected.json oracle stating, per case, which regression a correct detector must raise, at which severity, attributed to app or infra. tests/test_comparison.py asserts the engine against it.

Two candidate generators, two purposes. The recorded candidate is the committed fixture — the defect the author wrote, and the oracle's exact referent. The scripted candidate is built at run time by ScriptedRegressionAdapter, which injects one representative defect per category. Its four severity divergences (tu_arg_drift, tu_order_change, re_missing_evidence, re_wrong_source) are a property of that adapter, not a detector failure: it drops a tool rather than drifting an argument, and fabricates a claim rather than dropping a citation. Category recall is 18/18 on both paths, and the divergence is pinned in a test table rather than described.

at_failed_tool is the only case with two flags. Its candidate's compute tool fails (error_rate_regression, warn) and its answer degrades from "done" to "partial" (final_answer_regression, critical). The fixture note says exactly that. Every other defect raises exactly one flag, because a task_success drop is attributed to the category that owns the property that failed — without that rule, all 18 would also report a final_answer_regression.

The three rows that carry the argument

  • lc_latency_spike scores task_success = 1 on both sides. The answer is correct and byte-identical; only the process got slower (150 → 420 ms). A string-diff test sees nothing. The engine raises latency_regression.
  • at_infra_noise has a failed tool call and a red trace, and raises nothing. Its error is origin=infra, so the application is not blamed. The case is named in comparison_meta.json under infra_attributed_case_ids, not dropped — research question 9.
  • sj_control_reorder changes final_output and regresses nothing. The JSON keys were reordered; every metric is identical on both sides. A regression is a behavioral property getting worse, not a string changing.

Three rows carry the argument of this project:

  • lc_latency_spike scores task_success = 1 on both sides. The answer is correct and identical; only the process got slower. A string-diff test sees nothing. The latency percentiles see +65 ms at p95.

Reproducibility. Two runs on the same fixtures, in separate processes and into different output roots, produce byte-identical run.jsonl, run_meta.json, metrics.jsonl, comparison.jsonl, summary.json, and comparison_meta.json. Each writer re-hashes the file after writing and raises on any mismatch with its in-memory digest. Metric values are rounded at the boundary (six decimals; cost eight), so a score cannot differ in the last bit of a float between platforms.

The report (Milestone 7)

python3 scripts/06_generate_report.py renders the comparison above into results/reports/regression_report.md and .html. A copy of the Markdown is committed at docs/examples/regression_report.md, and a test regenerates it from the fixtures and compares byte for byte — a sample report in the docs that drifts from what the code emits is a claim nobody re-checks.

On the smoke comparison: verdict REGRESSED, 6 flags over 6 of 8 paired cases (4 critical, 2 warn), 6 clusters, lc_latency_spike in the latency table at +250.0 ms, and at_infra_noise in the disclosures as surfaced, excluded from flags — nowhere in the worst-regressions table.

LimitationsWhat the report cannot see

Three properties, each with a test. Deterministic — no clock, no RNG, no generation timestamp; two renders are byte-identical, and an AST scan fails if any module under reports/ imports time, datetime, random, secrets, socket, urllib, http, or requests. Redaction-masked, then gated fail-closed — free text is masked on the way into the report model, and the rendered document is then scanned for credential-like strings immediately before it is written; one that survived (necessarily in an identifier the redactor will not rewrite) is refused, and the error names the pattern and line without echoing the value. Sourced only from the artifacts — every string is a case id, a metric name, a threshold, or a rule-authored explanation; no model-generated output text is copied into it.

The HTML rendering is one self-contained file: no <link>, no <script>, no <img>, no url(), no external host. A report attached to a pull request should not tell a third party that someone is reading it.

Two cases errored on the candidate, and they are counted in different maps. at_more_retries is a genuine application error and moves error_rate alone. at_infra_noise has a failed tool call and a red request span, and moves infra_error_rate alone; it is named in infra_attributed_case_ids. A single flat map would have shown "2 errors out of 8" and let a broken harness look exactly like a broken model.

Harness degradation is not a regression, and there is a test for that too: zeroing one record's recorded latency drives incomplete_trace_rate to 0.125 and trace_completeness below 1.0 while success_rate stays at 1.0.

What a span does not claim: the trace records exactly one duration per case, so a child span's width is latency_ms / step_count — a slot, not a measurement. Every span is labeled recorded, derived or none. And spans carry identifiers and counts only: a test scans every span attribute of all 52 committed fixture records against the free text of the record it came from.

The cost guard (Milestone 11)

The one code path that could cost money, and the seven gates in front of it. Full reasoning on the Cost guard page.

ClaimEvidence
The adapter is inert by defaultApiAdapterStub() refuses before it stats a cache file — an ExplodingCache double proves the opt-in gate runs first

The estimator moved into pricing.py — a scored path — so the load-bearing result is that nothing downstream changed: sha256(run.jsonl) for the smoke baseline is still ee23bfde…, the value committed at Milestone 4; the comparison still detects the same six clusters; the committed example report regenerates byte-identically. Two adversarial checks were run rather than described: removing ledger.check(...) from the ladder fails 5 tests (including the one asserting the ceiling is checked before the transport is looked for); replacing the cache lookup with entry = None fails 6.

Test status

python3 -m pytest -q → 849 passed, CPU-only and offline (6 scaffold + 8 smoke + 54 schema + 25 fixtures + 46 adapters + 51 executor + 155 evaluators + 96 comparison + 67 reports + 70 observability + 73 redaction + 101 integration contracts + 97 API cost guard).

Offline is enforced, not assumed: an autouse fixture in conftest.py disables socket.socket.connect, connect_ex and socket.create_connection for every test in the repository, and one test asserts that fixture is armed.

What is not claimed

  • These are synthetic fixtures with injected defects. 18/18 recall shows the rules fire as specified, not recall on real regressions.
  • The eight controls test the specific false positives the fixtures encode (a key reorder, sub-threshold drift, harness noise). They are not a false-positive rate on real traffic.
  • No live model was called. No cost was incurred. Latency is recorded, not measured.
  • A child span's width is a slot, not a measurement. The trace records one duration per case; the partition asserts ordering only.

Redaction and safety hygiene (Milestone 9)

traces/redaction.py holds the one pattern table and the masking redactor. It runs before the executor hashes a run, before the report generator renders, and before the span writer writes. Twelve rules across two tiers; see Safety.

PropertyResult
Committed fixture records unchanged by redaction52 / 52, all clean
Smoke pipeline byte-identical to before the milestoneyes (run.jsonl, run_meta.json, regression_report.md)
llmreg scan-secrets on this repository0 findings
redaction_status values reachable and tested3 / 3 (clean, redacted, flagged)
Tests73 in tests/test_redaction.py (74 new; 651 total)

The first row is the load-bearing one. Redaction rewrites final_output before an evaluator ever reads it, so a false-positive mask would silently change a score. That all 52 records pass through untouched is what says the rules are tuned for this corpus — and the assertion lives in a test, so a future rule that starts rewriting scored text fails the suite rather than producing mysterious evaluator drift.

The three statuses are each reachable, which the schema's vocabulary would otherwise only claim: a clean record stays clean; a credential in final_output yields redacted and [REDACTED:openai_key] in the artifact; a credential in model_id — a join key — yields flagged and the executor refuses the run, naming the field and the pattern without echoing the value.

What will be reported next

Milestone 10 defines the integration contracts: trace import/export formats so a sibling repository can hand this one a run and get a comparison back. An imported trace is the first thing that can legitimately arrive flagged.

Reproduction

Every step runs today.

llmreg run-suite --suite evals/suites/smoke.yaml --adapter recorded \
    --app-version baseline  --out results/runs/
llmreg run-suite --suite evals/suites/smoke.yaml --adapter scripted-regression \
    --app-version candidate --out results/runs/
python3 scripts/04_score_runs.py                      # -> results/processed/

llmreg aggregate --run results/runs/smoke-baseline-recorded
llmreg aggregate --run results/runs/smoke-candidate-scripted-regression

llmreg compare --baseline results/runs/smoke-baseline-recorded \
    --candidate results/runs/smoke-candidate-scripted-regression \
    --out results/comparisons/                        # add --fail-on critical for CI

llmreg report --comparison results/comparisons/smoke-baseline-vs-candidate \
    --out results/reports/regression_report.md --format both

Without an editable install, use the wrappers python3 scripts/02_run_baseline.py, 03_run_candidate.py, 04_score_runs.py, 07_aggregate_runs.py, 05_compare_runs.py and 06_generate_report.py; all accept --dry-run to execute and summarize without writing. Generated results/ contents are gitignored and regenerated on demand.

All numbers are produced offline, CPU-only, and are byte-reproducible on the same fixtures. See docs/RESULTS.md and docs/REPRODUCIBILITY.md.
