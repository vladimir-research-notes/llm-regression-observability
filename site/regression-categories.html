Regression categories

A regression fires when a candidate is worse than the baseline by more than a threshold on a dimension. Detection is deterministic and threshold-driven — nothing is learned or fitted. Full rules in docs/REGRESSION_DETECTION.md.

status: Milestone 6 complete — all eight categories implemented in comparison/regression.py; 18/18 injected defects detected, 0 false positives on the 8 negative controls

Thresholds are the documented defaults; the detector reads them from the suite manifest, so they tune without code changes. An unknown threshold key is an error, not a shrug — a typo'd threshold that is silently ignored looks exactly like one being honored.

Severity

critical correctness lost: success 1→0 on an answer-level property, schema valid→invalid, a parse that stopped parsing, a disallowed tool, a missing tool call, a new unsupported claim, under-refusal. warn quality or efficiency degraded past a threshold: latency, cost, tool sequence or argument drift, partial evidence drop, a claim that lost its support, over-refusal, a risk-label move, a new app-origin error or retry. info reserved. A flag means a threshold was crossed, so the engine emits only warn and critical.

Two severity distinctions that carry weight

Under-refusal is critical; over-refusal is a warning. Answering something the baseline declined is a correctness failure. Declining something benign is a quality failure. Neither is visible in a string diff — "I'm sorry, but I can't help with that" is a perfectly well-formed answer.

A new unsupported claim is critical; a claim that lost its support is a warning. Both raise unsupported_claim_count from 0 to 1, so the count alone cannot separate them. The rule compares claim texts: re_unsupported_claim's candidate asserts something the baseline never said and cites nothing that backs it — the model invented a fact. re_wrong_source's makes the same claim but cites the wrong document — the model degraded its grounding.

One defect, one signal

task_success is the union of a case's declared expected_properties, and most of those belong to another dimension: json_schema_valid is the structured-output scorer's business, expected_tools is the tool scorer's. Flagging every task-success drop as a final_answer_regression would report every defect twice and turn flags_by_category into a histogram of itself.

So the drop is attributed. Each checkable property is owned by exactly one category, and final_answer_regression fires only when a newly-failed property is answer-level. On the fixtures, at_more_retries keeps its answer ("done") but violates max_tool_errors: 0: score_delta = −1.0, and the flag is error_rate_regression, which owns that property.

Within a category, several conditions can fire at once — a wrong tool is also a missing tool. They collapse into one flag per (case, category) carrying the strongest severity and naming the rest in its explanation.

Application vs. harness noise

Every degradation is attributed app (raises a flag) or infra (recorded, surfaced, but not flagged). A timeout on a flaky mock, a transport error, or a malformed fixture is harness noise. errors.attribution() returns infra only when a record errored and every error was infra-origin; one app error makes the whole record app. It is conservative on purpose — when in doubt it flags — because a missed regression is worse than a noisy one. This is the mechanism behind research question #9.

When a record is infra-attributed, the categories that would have fired are withheld and written to comparison_meta.json under infra_suppressed_categories. Nothing is silently dropped. The cost is real and documented: an application regression co-occurring with an infra error on the same case is masked. See Limitations.

Clustering

Flags group by failure signature — the specific way the candidate broke: schema_invalid, disallowed_tool:shell_exec, coverage_drop, app_error:tool_retry. The signature carries the offending symbol, because "the model started calling shell_exec" is a root cause and "a tool was wrong" is not.

No distance metric, no fitted grouping — two flags cluster when they share (category, signature), period. A fitted grouping could not be reproduced from the artifact alone, which is the same objection this project raises to learned judges. On the fixtures, three cases that each fail schema validation are one finding; a parse failure is a different root cause and clusters alone.

Ground-truth fixtures (Milestone 2)

Each category is backed by a synthetic fixture suite whose candidate cases carry a known, injected defect annotated with the category, severity, and attribution a correct detector must produce. This is the oracle Milestone 6 asserts against — detection becomes a stable test, not a hope. There are 26 cases: 18 injected defects and 8 negative controls (benign changes and sub-threshold drifts that must not flag).

Controlling false positives

  • Deterministic runs remove sampling variance.
  • Thresholds combine a relative and an absolute minimum, so jitter never fires.
  • Direction-aware: only worse moves flag. A faster, cheaper, more valid, more grounded, less error-prone candidate raises nothing.
  • A metric emitted on neither side — or on one side only — means not applicable, never zero.
  • The two placeholder scorers and the infra counters can never raise a flag: TRIGGER_METRICS ∩ NEVER_FLAG_METRICS = ∅, asserted at import.
  • field_diff_count is not a trigger — it counts extra fields regardless of additionalProperties, so a rise while validity holds means the schema permits the field.
  • Missing cases are reported unpaired, never scored as success.
  • Correlated failures are clustered so one root cause reads as one finding.

Measured on the committed fixtures: 18 injected defects, 18 detected, 0 missed, 0 false positives on the 8 negative controls. See Results.

Current test/result status

tests/test_comparison.py — 96 CPU-only tests. Detection is asserted twice: once against each fixture's own expected.json oracle, and once against a table pinning the complete flag set per case, so an extra flag fails as loudly as a missing one.

Open questions

  • Property ownership (max_tool_errors → error_rate_regression, expected_query → tool_call_regression) is a design decision, not a derived fact.
  • A refusal-decision flip is the one rule that fires on a change rather than a worsening. It is gated to cases where refusal is part of the task.
  • One flag per (case, category) keeps the runners-up only as prose in the flag's explanation; RegressionFlag has no detail field.
