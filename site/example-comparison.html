The case

From evals/fixtures/structured_json/cases.json. Expected behavior is declared as properties, never as a golden string.

case_id:  sj_invalid_json
prompt:   "Summarize the synthetic report as a JSON object with title, sentiment, and score."
json_schema:
  type: object,  additionalProperties: false
  required: [title, sentiment, score]
  properties:
    title:     {type: string}
    sentiment: {type: string, enum: [positive, neutral, negative]}
    score:     {type: number}
expected_properties: {json_parses: true, json_schema_valid: true}

Baseline vs candidate output

The baseline is replayed by the recorded adapter; the candidate is built by the scripted-regression adapter, which injects exactly one mechanical defect — here, it drops the closing brace.

baseline  (recorded):   {"title":"Q2 revenue summary","sentiment":"neutral","score":0.5}
candidate (scripted):   {"title":"Q2 revenue summary","sentiment":"neutral","score":0.5

changed_fields: ["final_output", "parsed_output"]
latency_ms: 180.0 -> 180.0        cost_estimate_usd: 0.0015 -> 0.0015

Scored deltas

Both sides are scored independently by the Milestone 5 evaluators; the comparison engine reads the two metric maps.

MetricBaselineCandidateDelta
json_parse_success1.00.0−1.0
json_schema_validity1.00.0−1.0
task_success1.00.0−1.0
field_diff_count0not emitted — a field diff against an object that does not exist would count one defect twice
latency_ms180.0180.00.0
trace_completeness1.01.00.0

trace_completeness stays at 1.0 deliberately. A candidate whose JSON genuinely broke has parsed_output = null, which is a correct trace of a real failure, not an incomplete one. Conflating the two would make a structured-output regression indistinguishable from a harness bug.

The resulting flag

Verbatim from comparison.jsonl:

{
  "category": "structured_output_regression",
  "severity": "critical",
  "metric": "json_parse_success",
  "observed": 0.0,
  "threshold": 1.0,
  "attribution": "app",
  "explanation": "final_output parsed as JSON at baseline and no longer does;
                  also: output was schema-valid at baseline and is not"
}

Three things did not happen, and each is a design decision:

  • Two triggers, one flag. The parse failure and the validity failure both fired. They collapse into a single flag carrying the stronger metric, naming the other in its explanation — so flags_by_category counts findings, not symptoms.
  • No final_answer_regression. task_success dropped 1 → 0, but the properties that failed (json_parses, json_schema_valid) are owned by the structured-output category. Flagging the drop again would report one defect twice.
  • No latency_regression. Latency did not move at all here — and even a +10 ms move would fail both floors (+50 ms absolute and +25% relative).

The control, for contrast

sj_control_reorder's recorded candidate emits the same object with its keys reordered. The raw string changed; not one metric did.

baseline:   {"title":"Weekly status","sentiment":"positive","score":0.7}
candidate:  {"score":0.7,"sentiment":"positive","title":"Weekly status"}

changed_fields:  ["final_output"]
regression_flags: []
human_readable_summary: "no regression: final_output changed; no metric crossed a threshold"

This is the whole argument in one case. A regression is a measurable behavioral property getting worse, not a string changing.

## What the engine declined to say

- **1 infra-attributed case(s)** — every error on the candidate record was
  harness-origin, so the application was not blamed: `at_infra_noise`.

Three things about that last section. It is not an appendix — it is the reason the report is trustworthy. at_infra_noise has a failed tool call and a red trace, and appears nowhere in the worst-regressions table. An unpaired case would be listed here too, and so would any flag withheld by infra attribution. A clean headline over a comparison that could only look at half its cases is the failure mode this project exists to avoid, and summary.json alone cannot show it — which is what comparison_meta.json is for.

The report carries no generation timestamp: it is a pure function of the comparison directory, so two renderings are byte-identical. Before the bytes are written, the whole document is scanned for credential-like strings and refused if one survived redaction (Milestone 9 supplies the mask; Milestone 7 supplies the gate). See Safety.

Reproduce it

python3 scripts/02_run_baseline.py
python3 scripts/03_run_candidate.py
python3 scripts/05_compare_runs.py            # add --fail-on critical for a CI gate
python3 scripts/06_generate_report.py         # -> results/reports/regression_report.{md,html}

Two invocations produce byte-identical artifacts.

Open questions

  • The scripted adapter injects one representative defect per category, so on four fixture cases its severity is harsher than the recorded candidate's. Category recall is 18/18 on both paths; see Results.
  • The report renders the collapsed flag's explanation string, so "wrong tool and missing tool and sequence drift" is one row, not three. Splitting them would need a structured detail field on RegressionFlag. See Limitations.
