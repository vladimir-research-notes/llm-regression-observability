Detecting regressions in stochastic, tool-using LLM systems

Model, prompt, tool, and deployment versions go in; evaluation traces, observability metrics, and regression reports come out. The system answers one hard question: when outputs are stochastic, multi-step, tool-using, and not reducible to exact string matching, did a change make behavior worse — and how?

status: Milestone 10 complete — the pipeline runs end to end (18/18 injected defects detected, 0 false positives on the 8 negative controls), a masking redactor runs in front of every write, and traces produced outside this repository now enter through versioned import contracts and are scored, compared and reported by the unchanged pipeline (2/2 injected defects detected on an imported code-agent session, 0 false positives); 752 tests passing

This is a reliability/evaluation framework, not a medical, legal, or security authority. All fixtures are synthetic. See Limitations and Safety.

Why exact match is not enough

Two correct answers can differ token for token. A valid JSON object can be phrased many ways. An agent can reach the right final answer through a worse process — more retries, more failed tool calls, a disallowed tool, twice the latency, twice the cost. A test that flags every string change is uselessly noisy; a test that watches only the final string is uselessly blind. So a regression is reframed as "a measurable behavioral property got worse," and measured across independent dimensions.

How it works

cases + adapter ──▶ RunRecords (traces) ──▶ ComparisonRecords ──▶ Report
   (baseline)                                    (deltas +
   (candidate)                                    regression flags)

A baseline run (known-good version) and a candidate run (the change) are executed over the same synthetic suite, compared case by case, scored on every dimension, flagged against configurable thresholds, clustered, and turned into a Markdown/HTML report. Deterministic mock / recorded / scripted-regression adapters make the whole pipeline runnable with no model call and no network.

Design constraints

  • CPU-only, target AWS m5.2xlarge. No GPU.
  • Offline and free by default — no test needs the internet or a paid API.
  • Dependency-free core — Python 3.12 standard library only; pydantic/pandas optional.
  • Deterministic — same inputs produce byte-identical outputs.
  • Any optional paid-API adapter is disabled by default and gated by dry-run, cost estimator, hard max-cost guard, response cache, and explicit opt-in.

Current implementation status

  • Project contract, plan, docs, milestone specs, and build harness — in place.
  • Milestone 0 — package skeleton, pyproject.toml (dependency-free core), llmreg CLI (version, check-env), and 14 CPU-only tests — complete.
  • Milestone 1 — typed data contracts in schemas.py (EvalCase, EvalSuite, RunRecord, tool/retrieval/error traces, MetricResult, ComparisonRecord, RegressionFlag, ReportSummary) with validation and byte-stable JSON; 54 schema tests — complete.
  • Milestone 2 — six synthetic fixture suites (26 cases: 18 injected defects + 8 controls) with per-case ground truth, a stdlib-only suite-manifest reader, and a fixture validator (llmreg validate-fixtures) covering schemas, referential integrity, real-defect and safety checks; 25 fixture tests — complete.
  • Milestone 3 — four deterministic adapters: MockModelAdapter, RecordedModelAdapter (replays the committed fixtures byte for byte), ScriptedRegressionAdapter (15 named injectors, planned from the ground-truth annotations), and an inert ApiAdapterStub; 46 adapter tests — complete.
  • Milestone 4 — the run executor: llmreg run-suite resolves a suite manifest, drives an adapter over every case, re-stamps run identity, accounts tokens/cost, and writes results/runs/<run_id>/run.jsonl plus a run_meta.json carrying totals and the SHA-256 of the records. Byte-stable persistence lives in traces/storage.py; 51 executor tests — complete.
  • Milestone 5 — the evaluators: ten deterministic scorer modules (task success, JSON schema validity, tool-call drift, evidence grounding, refusal shift, latency, cost, error classification, trace completeness, and a declared semantic placeholder), a stdlib JSON Schema validator, and METRIC_DIRECTION / NEVER_FLAG_METRICS so the comparison engine never hard-codes a sign or flags a placeholder. 155 tests assert exact expected scores for all 26 fixture cases on both sides — complete.
  • Milestone 6 — the comparison engine: llmreg compare pairs two runs by case_id (reporting unpaired cases), computes per-dimension deltas, raises RegressionFlags against suite thresholds with severity and app/infra attribution, clusters correlated failures, and writes comparison.jsonl + summary.json + comparison_meta.json. 18 of 18 injected defects detected with their annotated category and severity; 0 false positives on the 8 negative controls. 96 tests — complete.
  • Milestone 7 — the report generator: llmreg report reads a comparison directory and nothing else, then renders Markdown and one self-contained HTML file — verdict, per-category breakdown, worst regressions, a worked example per dimension, structured-output/latency/cost tables, failure clusters, and a section for what the engine declined to say (unpaired cases, infra-attributed cases, withheld flags, thresholds applied). Two decisions carry it. Selection happens once, in a shared ReportModel, so the two formats can never disagree about which rows are worst. Redaction is a fail-closed gate: the rendered document is scanned immediately before it is written, and a credential-like string that survived is refused rather than emitted — the masking redactor (Milestone 9) plugs into the same seam. No clock, no RNG, no generation timestamp, so two reports of one comparison are byte-identical. 66 tests — complete.
  • Milestone 8 — the observability layer: llmreg aggregate projects a run into an OpenTelemetry-shaped span tree (request → model_call / tool_call / retrieval / evaluator, no dependency) and reduces its per-case metrics to suite numbers. Three decisions carry it. Spans are derived, not emitted — a pure function of the artifact on disk, with content-addressed ids, so the tree is rebuildable and byte-identical; that is why the stage holding both the trace and the scores owns spans.jsonl. Only one duration was ever recorded: the request span reproduces latency_ms, its children get a partition of that interval that asserts ordering and not duration, evaluator spans are zero-width because scoring is post hoc, and every span is labeled with which. The suite summary keeps three maps — application scores, harness signals (trace_completeness, infra_error_rate), and declared placeholders — because a flat map lets a broken exporter and a broken model look alike. Spans carry identifiers and counts, never a prompt, an output, a tool argument value, or an error message. 70 tests — complete.
  • Milestone 9 — redaction and safety hygiene: traces/redaction.py is the one definition of "credential-like" in the repository, read by the trace writer, the span writer, the report gate and llmreg validate-fixtures. Four decisions carry it. Refuse on evidence, mask on suspicion — certain rules (provider key prefixes, JWT, Bearer, Authorization, private-key header) can block an artifact; heuristic rules (credential-named assignments, emails, generic high-entropy tokens) only mask, because a false-positive refusal is a denial of service on your own report. Identity fields are scanned, never rewritten — a case_id or a tool name is a join key, so a credential in one yields redaction_status="flagged" and the executor refuses the run rather than corrupt the artifact it claims to protect. The status is derived and only escalates (clean < redacted < flagged): an adapter claiming clean over a live secret is overruled, one claiming redacted is believed, and that monotone rule is what makes redaction idempotent in bytes and status. It runs inside execute_suite, not write_run — records_sha256 must digest the bytes that land on disk. All 52 committed fixture records pass through unchanged, so no scored text was rewritten; llmreg scan-secrets reports 0 findings on this tree. 73 tests — complete.
  • Milestone 10 — integration contracts: a trace produced outside this repository enters through an importer that maps it onto RunRecord, and everything downstream runs over it unchanged. Six importers ship (llmreg, code_agent_runtime, bioagentbench, bioscientist_os, agent_control_bench, claude_api) and no sibling repository is required, present, or read — their shapes are declared here and pinned against committed synthetic examples. Four rules define the contract: an importer may not drop a field in silence (an unmapped key refuses in strict mode), may not invent a measurement (a missing latency_ms imported as 0.0 reads as an improvement against a timed baseline and as an infinite regression when it is the baseline, so it is refused), may not guess an attribution (an unmapped error kind resolves to app and warns, because infra withholds flags), and may not import a secret (this is the edge Milestone 9 named: a credential in a join key refuses the import). Two imported code-agent sessions over the four-case external suite yield exactly the two injected defects and 0 false positives. 100 tests — complete.

Open questions / limitations

All fixtures are synthetic; results do not generalize to production traffic. Costs are transparent estimates, not bills. Some scorers (explanation quality, semantic similarity) are explicit placeholders. See Limitations.
