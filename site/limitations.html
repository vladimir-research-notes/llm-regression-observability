Limitations and non-goals

Being explicit about what this project does not do is part of the quality bar. Full text in docs/LIMITATIONS.md.

Synthetic fixtures

All cases are small and synthetic, designed to exercise each scorer and to carry known, injected regressions so the detector can be tested against ground truth. They are not a representative sample of any real workload; results on them do not generalize to production traffic.

No universal model evaluation

This is not a benchmark or a leaderboard. It measures relative behavioral change between a baseline and a candidate on a fixed suite. It does not rank models or certify that a model is good, safe, or correct.

Deterministic mocks, not live models

The default path uses mock / recorded / scripted adapters — reproducible and free, but tested against recorded behavior, not live stochasticity. Handling live-model variance (multiple samples, significance tests) is a documented future direction, not a current claim.

Estimated, not measured, cost

Token counts use a transparent char-based estimator and a fixture price table. Costs are estimates for relative comparison, not bills.

Recorded, not measured, latency

latency_ms is a value the trace reports; the executor never times the adapter, because a wall-clock read would put an ambient value into a scored field. The framework detects latency regressions as reported by the trace source, not as they occur on live infrastructure.

Placeholder scorers

explanation_quality_placeholder always emits 0.0 and claims nothing. semantic_similarity_stub is lexical token overlap — it rates a paraphrase low and a fluent contradiction high. Both are in NEVER_FLAG_METRICS, so the comparison engine cannot raise a regression from either, and both carry detail["placeholder"] = true.

Evidence support is recorded, not judged

Nothing here reads a snippet and decides whether it entails a claim; supported is a recorded field of the trace. An imported trace that never sets it scores every claim as unsupported — the conservative direction. citation_correctness checks only that a cited source_id exists, so a real document cited for the wrong claim is caught by unsupported_claim_count instead.

Not every declared property is checked

task_success scores against a closed vocabulary of structural property checks. Anything else a fixture declares is advisory: reported in the metric's detail, not scored. Today exactly one fixture property is advisory (expected_source_for_color — it is prose, and the defect it describes is caught by the evidence metrics), and one is pairwise (final_output_stable), which no single record can answer. A test pins the advisory set, so it cannot grow silently.

The JSON Schema validator is a subset

The core is dependency-free, so jsonschema is not an option. Keywords outside SUPPORTED_KEYWORDS ($ref, allOf, format, …) are surfaced in detail["unsupported_keywords"], never silently ignored — ignoring one would let an invalid document score as valid.

Heuristic attribution, and infra attribution can mask a real regression

The application-vs-infrastructure split is rule-based and conservative: a record is attributed to infrastructure only when every error on it is infra-origin, so one app error makes the whole record the application's fault. It reduces harness-noise false positives but can misattribute an unusual failure; it reports its confidence rather than claiming certainty.

The comparison engine acts on that verdict: when a candidate record is infra-attributed, every flag it would have raised is withheld, not just the error-rate one. That is right when the harness timed out — a timeout inflates latency, fails tool calls, and truncates output, and blaming the application for any of it would be wrong. But it means a genuine application regression that co-occurs with an infra error on the same case is masked. The engine does not hide this: the case appears in comparison_meta.json under infra_attributed_case_ids, and the withheld categories under infra_suppressed_categories. Re-running the suite is the remedy — an infra error should not reproduce, and an application regression will.

A flag is a threshold crossing, not a judgment of importance

Severity is assigned by rule (critical for correctness lost, warn for quality or efficiency degraded), not by impact. A critical flag on a synthetic fixture is not a claim that the change matters to any user. Likewise flags_by_category counts findings after collapsing one flag per (case, category); it is not a count of everything that moved.

The report can only say what the comparison artifacts say

llmreg report reads comparison.jsonl, summary.json and comparison_meta.json, and nothing else. That makes a report reproducible from a directory alone, at three costs. Deltas, not absolutes — the structured-output table shows -1 ("was valid, is not") rather than 1.0 → 0.0, because no artifact records the two values. A 0 row is ambiguous — in the per-category table it means no flag fired, and cannot distinguish a dimension evaluated and clean from one no case declared; the report prints all eight categories anyway, and says this in its own limitations note. A collapsed flag is one row — Milestone 6 folds a category's triggers into a single flag whose explanation names the runners-up after also:, and the report renders that string; splitting "wrong tool and missing tool and sequence drift" into three rows would need a structured detail field on RegressionFlag.

Redaction can rewrite text that a scorer then reads

traces/redaction.py masks a RunRecord's content fields before the record is hashed, persisted, or scored. That is the correct order for safety — and it means a false-positive mask changes a scored string. The heuristic tier (credential-named assignments, emails, generic high-entropy tokens) fires on suspicion by design, so a synthetic fixture containing a long mixed-class token would be scored on [REDACTED:high_entropy_token] rather than on its own text.

Three things bound the risk rather than eliminate it. The generic-token rule requires 24+ characters and mixed character classes and entropy above a prose floor, which clears SHA-256 digests, UUIDs and hyphenated run ids. redaction_status records that masking happened, so a surprising score has a visible cause. And a test asserts all 52 committed fixture records are byte-identical after redaction, so a future rule that starts rewriting scored text fails the suite rather than producing mysterious evaluator drift.

Identity fields are never rewritten, so pairing and tool-call diffing cannot be corrupted this way; a secret in one of those refuses the run instead. See Safety.

The entropy thresholds are tuned, not derived

The generic-token rule uses a 24-character minimum, a 3.2-bits-per-character entropy floor, and a mandatory lowercase + uppercase + digit filter. There is no false-positive/false-negative measurement behind those numbers — they were chosen against the strings this repository writes, and the character-class filter (not the entropy floor) is what clears a SHA-256 digest, whose entropy is 3.79. Any real corpus should re-tune them.

Span timings assert ordering, not duration

A trace records exactly one duration per case, latency_ms. The span tree gives the request span that recorded interval and hands its application children an equal partition of it, in trace order. A child span's width is latency_ms / step_count: a slot, not a measurement. Reading it as "the tool call took 63 ms" is wrong. Every span carries attributes["timing"] (recorded / derived / none) to say which it is, but a consumer that ignores that field will be misled. Cross-category interleaving is not recorded either, so the child order — model call, then tool calls, then retrievals — is canonical, not observed: a RAG trace and an agent trace get the same layout.

tool_error_rate_mean mixes app and infra origins

tool_error_rate is descriptive: an infra timeout fails a tool call just as an application bug does. Its suite mean therefore sits in application_metrics while counting both — on the smoke candidate it is 0.125, raised equally by at_more_retries (app) and at_infra_noise (infra). It cannot cause a false regression, because the error_rate_regression rule reads app_error_count and never this metric. But the suite number does blur the distinction the observability layer otherwise enforces. It is pinned by a test rather than quietly corrected, so a future fix has to be deliberate.

The observability layer has no consumer yet

spans.jsonl and aggregate.json are written, validated, and read by tests and by humans. Nothing downstream reads them: the comparison engine (Milestone 6) and the report generator (Milestone 7) predate the layer and still compute their own latency and cost statistics. A run's harness metrics therefore do not appear in the report's "what the engine declined to say" section, even though that is exactly where they belong.

Detection recall is measured on defects built to be detected

The 18/18 recall on Results is measured on synthetic fixtures whose defects were written alongside the rules that catch them. It shows that the rules fire as specified, that the eight negative controls do not fire, and that the pipeline is byte-reproducible. It is not evidence of recall on real regressions in real systems, and no such claim is made.

No production deployment

No server, no auth, no multi-tenant story, no persistence beyond local files (optional SQLite index is regenerable). This is a local-first research/engineering tool — and not a medical, legal, or security authority (see Safety).
